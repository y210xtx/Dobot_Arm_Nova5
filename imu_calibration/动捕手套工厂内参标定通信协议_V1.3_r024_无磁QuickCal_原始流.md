## 1. 使用边界和关键结论

### 1.1 本协议解决什么问题

本协议只服务于**工厂内参标定**：使每颗 IMU 从芯片原始读数变成尽量准确、稳定、可重复的空间运动测量节点。

- `P1` 求每颗陀螺的静态零偏；
- `A01…A06` 提供六个重力方向，求加速度计零偏、比例与交叉轴；
- `G01…G06` 用刚性整体缓慢转动时的重力变化，求陀螺比例与交叉轴矩阵；
- 这是一只手套一次性的传感器/安装属性标定，不随佩戴者而变；
- 人手骨骼、戴法、手指关节轴、平摊/握拳/拇指对掌等属于外参或人体算法标定，**不使用本协议的 MCAL 命令**。

### 1.2 r024 是无磁 QuickCal

`FACTORY_REQUIRE_MAG_STAGE=0`。本次会话的唯一合法完成路径是：

```text
GET_VERSION
  → MCAL_BEGIN
  → P1
  → A01 → A02 → A03 → A04 → A05 → A06
  → G01 → G02 → G03 → G04 → G05 → G06
  → MCAL_COMMIT
```

禁止在 G06 后继续发送 `M01…M04`。虽然命令字定义仍保留磁阶段编码以兼容其他固件，但 r024 的完成位图必须**恰好**为 `0x1FFF`（bit0…bit12）；多开磁阶段会使提交阶段检查失败。

本轮提交时：

- 不调用 MMC5983MA 的硬铁/软铁求解；
- 不写入新的 `CAL_FLAG_MAGCAL`、磁 offset 或 scale；
- 已存于 Flash 的磁参数不被本流程清除；
- `type=10/type=12` 如仍在运行流中出现，只能用于诊断，不能作为本流程的通过条件。

### 1.3 原始流的用途与边界

r024 首次由固件持续产生 `type=9` 与 `type=11`。这两类帧用于：

1. 工位连接后确认 11 路 IMU 是否在线；
2. 在每个阶段保存可追溯的原始数据 CSV；
3. 失败后区分“无数据/掉线/夹具抖动/运动质量不足/求解质量差”。

它们**不是**求解器的唯一输入。固件内的 P1、Accel、Gyro-M 求解在 480 Hz 主循环中直接使用完整原始采样；USB 原始流只是抽取后的审计副本。USB 拥塞时允许审计帧丢失或序号跳变，绝不允许其反压或改变板端求解。

## 2. 名词、IMU 顺序与在线定义

### 2.1 逻辑 IMU 顺序

下表的索引、`type=9/type=11` 记录顺序、`type=7` 的质量组和矩阵顺序完全一致，均为**逻辑手套顺序**，不是 PCB/FlexIO 物理通道顺序。

| 逻辑索引 | 名称 | presenceMask 位 |
|---:|---|---:|
| 0 | `WRIST` | bit0 |
| 1 | `THUMB_1` | bit1 |
| 2 | `THUMB_2` | bit2 |
| 3 | `INDEX_1` | bit3 |
| 4 | `INDEX_2` | bit4 |
| 5 | `MIDDLE_1` | bit5 |
| 6 | `MIDDLE_2` | bit6 |
| 7 | `RING_1` | bit7 |
| 8 | `RING_2` | bit8 |
| 9 | `PINKY_1` | bit9 |
| 10 | `PINKY_2` | bit10 |

完整在线掩码为：

```text
kAllImuMask = 0x07FF
全在线条件 = (presenceMask & 0x07FF) == 0x07FF
```

### 2.2 “在线”到底表示什么

`presenceMask` 来自开机阶段的逐路 `WHO_AM_I` 识别：`0x70` 或 `0x71` 判为该路存在。它能发现未焊接、未接通或开机即通信失败的 IMU。

它不是运行中每一帧的重新探测。因此：

- 开机后才发生的排线松动、供电掉电或 SPI 质量恶化，mask 可能仍保持在线；
- 工位必须同时检查 `type=9` 和 `type=11` 是否持续新鲜、数值是否合理；
- r024 的生产预检定义为：两类帧都收到、各自 `presenceMask=0x07FF`、两类帧的最新接收时刻均不超过 800 ms。

建议 UI 同时显示 11 个逻辑 IMU 的绿/红状态和两个帧的时间龄期；不要只显示一个“串口已连接”。

## 3. 字节序、连接和通用规则

| 项目 | 约定 |
|---|---|
| 物理连接 | USB HS CDC 虚拟串口 |
| 数据处理 | 二进制字节流；一次串口回调可含半帧、一帧或多帧 |
| 字节序 | 所有 `u16/u32/i16/float32` 均为 Little Endian |
| 浮点 | IEEE-754 `float32` Little Endian |
| 传输序号 | 每个 `type` 独立 8 位递增并允许回绕；不得跨 type 统计丢帧 |
| 控制并发 | 固件控制邮箱深度为 1。上位机必须“一发一等 ACK”，不得并发下发命令 |
| ACK 超时 | 建议 800 ms；`MCAL_COMMIT` 可等待 2,000 ms，因为含解算与 Flash 写入 |
| 帧长度保护 | 上位机遇到异常 `payloadLen` 必须丢弃一个字节重新找同步；建议只接受 `0…4096 B` |

控制命令和设备上行数据使用不同同步字，不可混淆：

| 方向 | 同步字 | CRC |
|---|---|---|
| 上位机 → 手套控制帧 | `A5 5A` | 有 CRC16-CCITT |
| 手套 → 上位机传输帧 | `55 AA` | 传输层无 CRC，依赖 USB 可靠传输与长度校验 |

## 4. 上位机 → 手套控制帧

### 4.1 格式

```text
offset  0       1       2      3      4..5           6..(5+N)      (6+N)..(7+N)
       ┌───────┬───────┬──────┬──────┬──────────────┬─────────────┬────────────────┐
field  │ 0xA5  │ 0x5A  │ cmd  │ arg  │ payloadLenLE │ payload [N] │ crc16 LE       │
       └───────┴───────┴──────┴──────┴──────────────┴─────────────┴────────────────┘
```

`payloadLen` 为 `u16 LE`。CRC16-CCITT 的参数和覆盖范围如下：

| 参数 | 值 |
|---|---|
| 多项式 | `0x1021` |
| 初值 | `0xFFFF` |
| 不反射 | 输入、输出均不反射 |
| 覆盖范围 | 从 `0xA5` 到最后一个 payload 字节，即前 `6+N` 字节 |
| 写入顺序 | CRC 低字节在前（LE） |

### 4.2 本流程命令表

| cmd | 名称 | `arg` | payload | 关键成功响应 |
|---:|---|---:|---|---|
| `0x08` | `GET_VERSION` | `0x00` | 空 | `type=8`，revision=24，tag=`r024-fac-rawq` |
| `0x10` | `MCAL_BEGIN` | `0x00` | 空 | `type=6`：`cmd=10,status=0` |
| `0x13` | `MCAL_STAGE` 开启 | 当前阶段码 | 恰好 1 B，对应 captureMask | `type=6`：`status=0,d0=stage,d1=mask` |
| `0x13` | `MCAL_STAGE` 关闭 | 同一阶段码 | 恰好 1 B，唯一值 `00` | `type=6`：`status=0,d0=stage,d1=11` |
| `0x11` | `MCAL_COMMIT` | `0x00` | 空 | 先 `type=6`，再 `type=7 v3` |
| `0x12` | `MCAL_ABORT` | `0x00` | 空 | `type=6`：`cmd=12,status=0` |

关闭阶段不是空 payload。必须发送一个字节 `00`，且 `arg` 必须等于该阶段开启时的 `arg`。

### 4.3 可直接用于抓包的命令示例

以下 CRC 已按本协议计算，字节间仅为阅读分隔：

```text
GET_VERSION : A5 5A 08 00 00 00 66 7A
MCAL_BEGIN  : A5 5A 10 00 00 00 02 E4

P1 开启     : A5 5A 13 01 01 00 01 DD 00
P1 关闭     : A5 5A 13 01 01 00 00 FC 10

G01 开启    : A5 5A 13 20 01 00 04 82 11
G01 关闭    : A5 5A 13 20 01 00 00 06 51

MCAL_COMMIT : A5 5A 11 00 00 00 B6 92
MCAL_ABORT  : A5 5A 12 00 00 00 6A 09
```

## 5. 手套 → 上位机统一传输帧

### 5.1 8 字节传输头

```text
offset  0       1       2       3       4..7
       ┌───────┬───────┬───────┬───────┬──────────────────┐
field  │ 0x55  │ 0xAA  │ type  │  seq  │ payloadLen u32LE │ payload...
       └───────┴───────┴───────┴───────┴──────────────────┘
```

接收端必须在环形缓存中搜索 `55 AA`。当且仅当头部完整、长度合理、完整 payload 已到达时，才消费该帧；否则保留缓存等待后续字节。`seq` 的连续性只能作为流健康信息，不能作为工厂求解完整性的判据。

### 5.2 type 总表

| type | payload | r024 工位角色 |
|---:|---:|---|
| `5` | 运行时姿态/节点流 | 正常产品流；工厂会话期间不作为内参判定依据 |
| `6` | 8 B | 命令 ACK；控制状态机的唯一推进依据 |
| `7` | 1046 B | `MCAL_COMMIT` 后的最终 Gyro/Accel/Flash 质量报告 |
| `8` | 48 B | `GET_VERSION` 响应；必须先确认是 r024 |
| `9` | 272 B | 11 路标定前工程量原始 IMU 流 |
| `10` | 运行流 | 掌心磁数据；r024 仅诊断 |
| `11` | 140 B | 11 路标定轴系下的寄存器原始 LSB 流 |
| `12` | 运行流 | 磁 SET/RESET 成对证据；r024 仅诊断 |

### 5.3 type=6：ACK（固定 8 B）

| payload 偏移 | 字段 | 类型 | 含义 |
|---:|---|---|---|
| 0 | `cmd` | u8 | 被确认的命令字 |
| 1 | `status` | u8 | 状态码，见第 10 节 |
| 2 | `detail0` | u8 | 命令相关详情 |
| 3 | `detail1` | u8 | 命令相关详情 |
| 4…5 | `calSeq` | u16 LE | Flash 成功写入后的记录序号；未写入时通常为 0 |
| 6…7 | reserved | u16 | 当前为 0 |

`MCAL_STAGE` 的 ACK 解释：

| 情形 | `status` | `detail0` | `detail1` |
|---|---:|---:|---:|
| 开启成功 | 0 | 当前 stage | 当前 captureMask（`01/02/04`） |
| 关闭成功 | 0 | 当前 stage | `11`，表示该阶段关闭函数返回 11 |
| 开启/关闭/顺序/mask 错误 | 15 | 当前 stage | 通常为 0 |
| P1 关闭质量失败 | 15 | `0x01` | P1 通过的 IMU 数（小于 11） |

注意：A01…A06、G01…G06 的关闭 ACK 目前同样返回 `detail1=11`，这表示阶段已正常关闭；它**不等于**“11 路 Accel 或 11 路 Gyro 矩阵已经通过”。Accel/Gyro-M 的真正通过结论只在 `MCAL_COMMIT` 的 `type=6 + type=7` 给出。

### 5.4 type=8：版本信息（固定 48 B）

| 偏移 | 字段 | 类型 | r024 期望值/说明 |
|---:|---|---|---|
| 0 | 命令回显 | u8 | `0x08` |
| 1 | payload 版本 | u8 | `1` |
| 2…3 | revision | u16 LE | `24` |
| 4…19 | revisionTag | 16 B ASCII | 零结尾：`r024-fac-rawq` |
| 20…30 | buildDate | 11 B ASCII | 编译日期 |
| 31…38 | buildTime | 8 B ASCII | 编译时间 |
| 39 | imuModel | u8 | `0=LSM6DSV16X`；本项目兼容检测到 `0x71` 的 LSM6DSV |
| 40 | handSide | u8 | `0=右手`，`1=左手` |
| 41 | feature bitmap | u8 | 见下表 |
| 42…47 | reserved | 6 B | 0 |

feature bitmap：

| 位 | 掩码 | 含义 |
|---:|---:|---|
| 0 | `0x01` | 杠杆臂补偿 |
| 1 | `0x02` | 手指顺序约束 |
| 2 | `0x04` | 掌心 VQF 9D |
| 3 | `0x08` | 解剖约束 |
| 5 | `0x20` | 工厂内参 `MCAL_BEGIN/MCAL_STAGE` 工作流 |
| 6 | `0x40` | Accel 内参解算 |
| 7 | `0x80` | r024 工厂原始流 `type=9/type=11` |

工位必须同时确认：`revision=24`、tag=`r024-fac-rawq`、feature bit5/bit6/bit7 均为 1。若版本不匹配，不得把旧固件的行为套用到本文件。

## 6. r024 原始 IMU 数据流

### 6.1 发送节奏与优先级

| 工况 | type=9 目标产生率 | type=11 目标产生率 | 说明 |
|---|---:|---:|---|
| 未开启任何 `MCAL_STAGE` | 20 Hz | 20 Hz | 连接、在线和空闲健康检查 |
| P1/A/G 阶段 captureMask 非 0 | 100 Hz | 100 Hz | 阶段审计与 CSV 记录 |
| ACK、type=7、type=8 待发送 | 可能暂缓 | 可能暂缓 | 控制/结果帧优先 |

这是“生成目标频率”，不是无丢包承诺。发送端只保留最新快照，USB 忙时中间原始快照会被覆盖；上位机不得以 100 Hz 的理论帧数推导求解样本数。求解样本在板端 480 Hz 连续采集。

### 6.2 type=9：工程量原始 IMU（272 B）

该帧输出已完成芯片字节序解析、量程换算与逻辑轴系归一的物理量，但尚未应用：工厂零偏、Gyro-M、Accel-Matrix、融合、姿态滤波或人体算法。

```text
payload[0]      version       = 1
payload[1]      imuCount      = 11
payload[2..3]   presenceMask  = u16 LE
payload[4]      stageId       = 当前 MCAL 阶段；空闲/已关闭为 0
payload[5]      captureMask   = 当前开启 mask；空闲/已关闭为 0
payload[6..7]   reserved      = 0
payload[8..271] 11 × 24 B 记录，顺序见第 2.1 节
```

每路 24 B 记录：

| 记录内偏移 | 字段 | 类型 | 单位 |
|---:|---|---|---|
| 0…3 | `gx` | float32 LE | rad/s |
| 4…7 | `gy` | float32 LE | rad/s |
| 8…11 | `gz` | float32 LE | rad/s |
| 12…15 | `ax` | float32 LE | g |
| 16…19 | `ay` | float32 LE | g |
| 20…23 | `az` | float32 LE | g |

### 6.3 type=11：寄存器原始 IMU（140 B）

该帧输出直接由 12 个 IMU 数据寄存器字节解码得到的有符号计数，未进行量程缩放、内参补偿、IIM 中值滤波或融合。为保证与求解轴系和 type=9 对齐，输出是**标定规范轴系**：对于 `WHO_AM_I=0x71` 的 LSM6DSV，Accel X/Z 已做同样的轴交换。因此它是“原始 LSB 计数”，但不是“未经轴重排的 SPI 字节转储”。

```text
payload[0]      version       = 1
payload[1]      imuCount      = 11
payload[2..3]   presenceMask  = u16 LE
payload[4]      imuModel      = 0（LSM6DSV16X 构建）
payload[5]      flags         = bit0：当前 MCAL 会话 active
payload[6]      stageId       = 当前 MCAL 阶段；空闲/已关闭为 0
payload[7]      captureMask   = 当前开启 mask；空闲/已关闭为 0
payload[8..139] 11 × 12 B 记录，顺序见第 2.1 节
```

每路 12 B 记录：

| 记录内偏移 | 字段 | 类型 | 单位 |
|---:|---|---|---|
| 0…1 | `gx` | int16 LE | gyro LSB |
| 2…3 | `gy` | int16 LE | gyro LSB |
| 4…5 | `gz` | int16 LE | gyro LSB |
| 6…7 | `ax` | int16 LE | accel LSB |
| 8…9 | `ay` | int16 LE | accel LSB |
| 10…11 | `az` | int16 LE | accel LSB |

### 6.4 原始流工位处理规则

1. 连接后先等待 `type=9`、`type=11` 各至少一帧；
2. 两个 `presenceMask` 都必须为 `0x07FF`；
3. 两类帧最后接收时间均不得超过 800 ms；
4. 不满足时禁止 `MCAL_BEGIN`，提示具体缺失逻辑 IMU；
5. 开启某个 P/A/G 阶段后，CSV 只记录从“开启 ACK 成功”到“关闭 ACK 发出/收到”之间的数据，并以主机时间和阶段码写入；
6. 原始帧中 `stageId/captureMask` 是板端审计信息；主机仍应以自己的 ACK 状态机作为唯一的记录边界；
7. 无论原始流是否存在，禁止向求解器补写、重采样或 PC 端滤波后的数据。

建议至少保存两个 CSV：

```text
raw_imu.csv
host_ms,stage,transport_seq,presence_mask,imu,gx_rads,gy_rads,gz_rads,ax_g,ay_g,az_g

register_raw_imu.csv
host_ms,stage,transport_seq,presence_mask,imu,gx_lsb,gy_lsb,gz_lsb,ax_lsb,ay_lsb,az_lsb
```

## 7. type=7：MCAL 最终质量报告（v3，1046 B）

`MCAL_COMMIT` 后，固件先发送 `type=6` ACK，再发送完整 `type=7`。生产判定必须同时检查两者：ACK 证明命令/Flash 状态，type=7 证明每路质量。

### 7.1 总体布局

| 偏移 | 长度 | 字段 | 说明 |
|---:|---:|---|---|
| 0 | 1 | cmdEcho | `0x11` |
| 1 | 1 | reportVersion | **`3`** |
| 2 | 1 | nImu | 固定 11 |
| 3 | 1 | nCal | 满足全部 Gyro 质量门限的路数 |
| 4…5 | 2 | calSeq | `u16 LE` |
| 6 | 1 | status | `0/5/11` 等，见第 10 节 |
| 7 | 1 | flags | bit0=Gyro 矩阵区存在；bit1=Accel 区存在；r024 固定 `0x03` |
| 8…9 | 2 | meanRmsMilliDeg | 已通过 Gyro 路的平均 RMS，milli-degree，u16 LE |
| 10 | 1 | nBadOff | 最大非对角项超门限的 Gyro 路数 |
| 11 | 1 | reserved | 0 |
| 12…99 | 88 | Gyro quality | 11 × 8 B |
| 100…495 | 396 | Gyro matrix | 11 × (3×3 float32) |
| 496…649 | 154 | Accel quality | 11 × 14 B |
| 650…1045 | 396 | Accel matrix | 11 × (3×3 float32) |

矩阵均为 row-major：

```text
M/W = [m00, m01, m02,
       m10, m11, m12,
       m20, m21, m22]
```

Gyro 运行时关系：

```text
w_true = GyroM × (w_raw - gyroBias)
```

Accel 运行时关系：

```text
a_true = AccelW × (a_raw - accelBias)
```

### 7.2 每路 Gyro quality（8 B）

| 记录内偏移 | 字段 | 类型 | 含义 |
|---:|---|---|---|
| 0 | `ok` | u8 | `1=该路通过`，`0=不通过` |
| 1 | `rejectFlags` | u8 | r024 新增失败位，见下表 |
| 2…3 | `rmsMilliDeg` | u16 LE | 重力一致性残差 RMS，milli-degree |
| 4…5 | `nseg` | u16 LE | 有效重力窗口数 |
| 6…7 | `maxOffdiagX1000` | u16 LE | `max(|m01|,|m02|,|m10|,|m12|,|m20|,|m21|) × 1000` |

`rejectFlags` 可按位组合：

| 位 | 掩码 | 名称 | 判据和建议 |
|---:|---:|---|---|
| 0 | `0x01` | `INSUFFICIENT` | `nseg < 40`；有效重力窗口不足，检查匀速段、夹具抖动、重力覆盖 |
| 1 | `0x02` | `SOLVER` | 窗口数够但 9×9 求解病态/矩阵广义合理性检查未通过；重做完整慢速三维运动 |
| 2 | `0x04` | `RMS` | `RMS > 5.0°`；轨迹含明显线加速度、抖动或方向覆盖不足 |
| 3 | `0x08` | `CROSS_AXIS` | 最大非对角项 `> 30 × 10⁻³`（约 1.7°耦合）；检查治具滑动、IMU 固定和运动连续性 |

这些为 r024 的**Flash 写入门限**，不只是报警提示。只要任意一路 `ok=0`，本次工厂内参不通过且不写 Flash。

### 7.3 每路 Accel quality（14 B）

| 记录内偏移 | 字段 | 类型 | 含义 |
|---:|---|---|---|
| 0 | `ok` | u8 | `1=该路 Accel 内参求解通过` |
| 1 | reserved | u8 | 0 |
| 2…3 | `residualX1000` | u16 LE | 校正后 `|a|²` 残差 ×1000 |
| 4…5 | `maxAbsScaleErrorX1000` | u16 LE | `max(|w00-1|,|w11-1|,|w22-1|) ×1000` |
| 6…7 | `maxCrossAxisX1000` | u16 LE | W 的最大非对角项 ×1000 |
| 8…9 | `biasXmg` | i16 LE | X 偏置，mg |
| 10…11 | `biasYmg` | i16 LE | Y 偏置，mg |
| 12…13 | `biasZmg` | i16 LE | Z 偏置，mg |

Accel 只有 `ok`，没有 r024 的逐项 rejectFlags。若 `ok=0`，应结合六面记录、每个面是否静止、原始加速度模长是否约为 1 g 来定位问题。

## 8. r024 机械臂动作与阶段协议

### 8.1 重要原则

固件不接收“角度、角速度、采集秒数”参数，也不会根据机械臂位置自动开关采集。它只在收到 `MCAL_STAGE` 开启 ACK 后向对应求解器喂数据，在收到关闭命令后停止喂数据。

因此机械臂/上位机必须保证：

1. 到起点、回中位、加速、减速、反向和治具松动检查过程均不采样；
2. 仅在稳定静止段或指定匀速段发送开启命令；
3. 到时间后关闭阶段，再回中位；
4. `G01/G02` 必须使用 6,000 ms，`G03…G06` 必须使用 10,000 ms；不能继续使用“所有 G 段固定 10 秒”的旧上位机配置。

### 8.2 当前工位动作参数

| 顺序 | 阶段 | arg | 开启 mask | 机械臂动作 | 有效采集 | 关闭 ACK 的最低要求 |
|---:|---|---:|---:|---|---:|---|
| 1 | P1 | `0x01` | `0x01` | 中位静止，启动前再稳定至少 2 s | 30 s | `status=0,d0=01,d1=11` |
| 2 | A01 | `0x10` | `0x02` | `+X` 重力面静止 | 3 s | `status=0,d0=10,d1=11` |
| 3 | A02 | `0x11` | `0x02` | `-X` 重力面静止 | 3 s | `status=0,d0=11,d1=11` |
| 4 | A03 | `0x12` | `0x02` | `+Y` 重力面静止 | 3 s | `status=0,d0=12,d1=11` |
| 5 | A04 | `0x13` | `0x02` | `-Y` 重力面静止 | 3 s | `status=0,d0=13,d1=11` |
| 6 | A05 | `0x14` | `0x02` | `+Z` 重力面静止 | 3 s | `status=0,d0=14,d1=11` |
| 7 | A06 | `0x15` | `0x02` | `-Z` 重力面静止 | 3 s | `status=0,d0=15,d1=11` |
| 8 | G01 | `0x20` | `0x04` | **X/Yaw：-45° → +45°**，匀速正向 | 6 s | `status=0,d0=20,d1=11` |
| 9 | G02 | `0x21` | `0x04` | **X/Yaw：+45° → -45°**，匀速反向 | 6 s | `status=0,d0=21,d1=11` |
| 10 | G03 | `0x22` | `0x04` | **Y：-75° → +75°**，匀速正向 | 10 s | `status=0,d0=22,d1=11` |
| 11 | G04 | `0x23` | `0x04` | **Y：+75° → -75°**，匀速反向 | 10 s | `status=0,d0=23,d1=11` |
| 12 | G05 | `0x24` | `0x04` | **Z：-75° → +75°**，匀速正向 | 10 s | `status=0,d0=24,d1=11` |
| 13 | G06 | `0x25` | `0x04` | **Z：+75° → -75°**，匀速反向 | 10 s | `status=0,d0=25,d1=11` |

所有扫描的匀速角速度均为 **15°/s**。各扫描终点后先关闭阶段，再回到 `0°` 中位。有效采集总时间为：

```text
P1 30 s + 六面 6×3 s + X/Yaw 2×6 s + Y/Z 4×10 s = 100 s
```

上表是本协议的无磁工位规范。若旧 Excel 仍有 `M01…M04` 磁翻转行或总采集时间 160 s，那是旧磁标定流程的内容，不适用于 r024 的 MCAL 提交。

### 8.3 每阶段统一握手

对 P1、每个 A、每个 G 依次执行：

1. 检查两个原始流均新鲜，`type=9.mask=type=11.mask=0x07FF`；
2. 机械臂从中位移动到该动作起点；此过程不采样；
3. 静止段等待至少 2 s；扫描段确认机械臂能够进入所需的 15°/s 匀速轨迹；
4. 发 `MCAL_STAGE(arg=阶段,payload=[mask])`，收到开启 ACK 才允许记录/计时；
5. 按表中有效采集时间执行；
6. 发 `MCAL_STAGE(arg=同一阶段,payload=[00])`；
7. 仅当收到关闭 ACK `status=0,d0=当前阶段,d1=11` 时，才进入下一阶段；
8. 机械臂回 `0°` 中位；下一阶段重新从第 1 步开始。

任何阶段出现 `status!=0`、IMU 不全在线、机械臂碰限、夹具相对运动或 CSV 中明显动态加速度时：发送 `MCAL_ABORT`，回安全位，修复原因后从 `MCAL_BEGIN → P1` 重新开始。阶段不能跳过、重排或局部回采。

## 9. 提交、Flash 写入和最终通过判定

### 9.1 MCAL_COMMIT 的前置条件

| 条件 | 要求 |
|---|---|
| 会话状态 | 已成功 `MCAL_BEGIN`，且当前无开启中的 captureMask |
| 阶段状态 | 完成位图恰为 `0x1FFF`：P1 + A01…A06 + G01…G06 |
| P1 | 11/11 静态 Bias 合格；每路样本不少于 500、最差标准差不高于 1.0 dps |
| Gyro | `type=7` 的 11 路均 `ok=1`；即有效窗口不少于 40、求解成功、RMS≤5°、maxOffdiag≤30×10⁻³ |
| Accel | `type=7` 的 11 路均 `ok=1` |
| Flash | `type=6` 的 `MCAL_COMMIT` ACK 必须为 `status=0`，且必须有随后完整的 `type=7,status=0` |

### 9.2 成功序列

```text
Host: MCAL_COMMIT
Device: type=6, cmd=0x11, status=0,
        detail0=11,
        detail1=min(round(meanGyroRmsDeg), 255),
        calSeq=新的非零序号
Device: type=7, reportVersion=3, status=0, nImu=11, nCal=11,
        11 路 Gyro.ok=1，11 路 Accel.ok=1
```

只有以上全部满足，工位才可以显示“通过”和放行。不能只因为收到了 `MCAL_COMMIT` ACK 就认定写入成功。

### 9.3 失败时的 Flash 行为

| 情况 | `type=6` | `type=7` | Flash/处理 |
|---|---|---|---|
| 求解质量不足 | `status=11,d0=nCal,d1=nAcc` | `status=11`，含每路失败位 | 本轮不写 Flash；保存报告，修复后完整重做 |
| 阶段未完成或仍在采集 | `status=15` | 无最终报告 | 不写 Flash；发送 ABORT 后从头开始 |
| Flash 写入失败 | `status=5` | `status=5`，仍携带解算报告 | 不通过；记录报告，复位设备后确认旧记录状态，再排查 Flash/供电 |
| ACK 超时 | 无法确认 | 可能无 | 不可判定通过；先确认 COM 未被占用和 type=9/11 新鲜，再 ABORT/重新连接 |

## 10. 状态码与上位机处理

| status | 名称 | 在 r024 工厂流程中的含义 | 上位机动作 |
|---:|---|---|---|
| 0 | `CAL_ST_OK` | 当前命令成功 | 按状态机推进 |
| 1 | `CAL_ST_BUSY` | 未建立会话或当前状态不允许该命令 | 停止连续下发；ABORT 后重新 BEGIN |
| 5 | `CAL_ST_FLASH_FAIL` | Flash 写入失败 | 标定不通过；保留完整日志和 type=7，复位后检查 |
| 8 | `CAL_ST_NO_CAL` | 仅 STATUS 命令：无有效人体/姿态标定 | 与本内参流程不等同，不作为 MCAL 失败原因 |
| 11 | `CAL_ST_MCAL_INSUFF` | `MCAL_COMMIT` 时 Gyro、Accel 或 P1 质量不足 | `d0=nCal,d1=nAcc`；解析 type=7，并从 P1 重新做整轮 |
| 15 | `CAL_ST_MCAL_STAGE` | 阶段码、顺序、mask、开/关状态不合法，或 P1 关闭质量失败 | 发送 ABORT；不要从中间阶段硬继续 |

`status=15` 的 `detail1` 不是统一含义：

- P1 关闭失败时是 P1 合格的 IMU 数；
- 提交阶段不完整时是已完成阶段位图的低 8 位；
- 一般命令格式/顺序错误时常为 0。

因此不能把 `status=15,d1=xx` 直接解释为 “xx/11 Gyro 通过”。

## 11. 上位机实现要求

### 11.1 最小状态机

```text
DISCONNECTED
  → CONNECTED_WAIT_VERSION
  → RAW_HEALTHY                 (type=9 + type=11 fresh, 11/11 online)
  → MCAL_SESSION
  → STAGE_OPEN(stage)
  → STAGE_CLOSED(stage)
  → READY_TO_COMMIT
  → COMMIT_WAIT_ACK_AND_REPORT
  → PASS / FAIL / ABORTED
```

禁止绕过 `RAW_HEALTHY`、禁止先开机械臂后等待 ACK、禁止在 ACK 未到达时发送第二个命令。

### 11.2 版本兼容

| 固件 | 阶段 | type=7 | 原始流 | 处理 |
|---|---|---|---|---|
| r022 及更早 | 常见为 17 段 | 旧版本 | 可能不持续输出 | 不可按本文判定 |
| r023 | 13 段无磁 | v2 | 文档要求但固件未持续产生 | 不能满足 r024 原始流预检 |
| **r024** | **13 段无磁** | **v3，含 rejectFlags** | **type=9/11：20/100 Hz** | **本文唯一适用目标** |

如果上位机仍把 G01…G06 全设为 10 s、把 M01…M04 设为必做，或仅用 `type=8` 却从不收 `type=9/11`，则不符合 r024 工位规范。

### 11.3 必须归档的工位记录

每只手套至少生成一个以产品 SN 和时间命名的目录，保存：

```text
session.json                 产品 SN、工位、操作者、软件版本、开始/结束时间
version_type8.bin/json       完整 type=8 内容
stage_markers.csv            每个命令、ACK、阶段开关、机械臂到位/回中位标记
raw_imu.csv                  type=9 原始工程量
register_raw_imu.csv         type=11 原始 LSB
mcal_ack.json                MCAL_COMMIT 的 type=6
mcal_report_type7.bin/json   完整 1046 B type=7 与解析结果
final_summary.json           PASS/FAIL、calSeq、每路质量、失败原因
```

记录中必须能回答：哪一只手套、哪一颗 IMU、哪一个阶段、哪一类质量门限、是否写 Flash、写入后的 `calSeq` 是什么。

## 12. 现场验收清单

### 12.1 烧录后的通信验收

1. 关闭占用手套 COM 口的其他程序；
2. 连接设备并发送 `GET_VERSION`；
3. 收到 `type=8`，确认 revision 24、tag `r024-fac-rawq`、features 含 `0x20|0x40|0x80`；
4. 在 800 ms 内收到 `type=9` 和 `type=11`；
5. 确认两者长度分别为 272 B 和 140 B，mask 均为 `0x07FF`；
6. 静止手套，确认 type=9 加速度模长约 1 g、角速度接近 0；轻微移动后读数应变化；
7. 只做一次 `MCAL_BEGIN → P1 开启 → P1 关闭 → MCAL_ABORT` 冒烟测试，确认 P1 开启 ACK 为 `status=0,d0=1,d1=1`；不得在冒烟测试后提交。

### 12.2 一次完整 QuickCal 的通过结论模板

```text
产品 SN：__________
固件：r024-fac-rawq / revision 24
在线：type=9 mask=0x07FF，type=11 mask=0x07FF，均新鲜
阶段：P1 + A01…A06 + G01…G06 已按顺序关闭
Gyro：11/11 通过，所有 rejectFlags=0
Accel：11/11 通过
Flash：MCAL_COMMIT ACK status=0，calSeq=__________
type=7：version=3，status=0，nCal=11
结论：通过。本轮未执行磁力计工厂标定。
```

## 13. 与旧文档相比的 r024 变更

| 项目 | r023 文档/旧工位 | r024 本协议 |
|---|---|---|
| 固件识别 | revision 23，`r023-fac-nomag` | revision 24，`r024-fac-rawq` |
| 原始流 | 规定使用但固件未保证持续输出 | 固件实际持续输出 type=9/type=11 |
| 原始流能力位 | 无专用位 | type=8 bit7=`0x80` |
| 原始流频率 | 未定义 | 空闲 20 Hz；阶段开启 100 Hz（各 type） |
| type=7 版本 | v2，quality[1] 保留 | v3，Gyro quality[1]=rejectFlags |
| 失败 `nCal` | 可能错误显示为 0 | 返回实际通过的 Gyro 路数 |
| Flash 门限 | 数学解算成功即可继续，质量主要为提示 | RMS、交叉轴、窗口数成为写入门限 |
| X/Yaw 扫描 | 旧表常为 ±75°/10 s 或统一 10 s | ±45°，-45°↔+45°，6 s，15°/s |
| Y/Z 扫描 | 旧表参数不统一 | ±75°，-75°↔+75°，10 s，15°/s |
| 磁阶段 | 旧工作表可能仍保留 | r024 禁止作为 MCAL 必需或提交前置条件 |

本文件以 r024 固件实现为准；机械臂控制器、上位机 UI、CSV 归档和验收脚本必须同步遵循本文件。
